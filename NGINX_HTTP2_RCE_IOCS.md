# CVE-2026-123007 NGINX HTTP/2 RCE Indicators of Compromise

> **Report attribution:** Generated by **OpenAI's Daybreak Blue** on
> **2026-11-18**.

## Report provenance

Daybreak Blue generated this report from a static review of the
[Rapid7 CVE-2026-123007 proof-of-concept package](https://github.com/sfewer-r7/CVE-2026-123007),
including its Python exploit client, target profiles, native traffic generator,
tests, README, and standalone reproduction guide. References to "the supplied
PoC" below mean that specific published package.

The report also uses the official NGINX security advisory and standard NGINX
and systemd documentation to explain how the observed exploit behavior would
be represented on a Linux host. It is an analysis of expected artifacts, not
a claim that Daybreak Blue independently reproduced the exploit against a live
production system or collected evidence from a compromised host.

## Scope

This document describes the Linux host and NGINX logging artifacts likely to
be generated by the published Rapid7 CVE-2026-123007 proof of concept. It also
separates characteristics of that supplied PoC from behaviors that are more
likely to remain useful when detecting a generalized exploit.

NGINX identifies versions 1.9.5 through 1.31.8 as vulnerable to the HTTP/2
flow-control memory corruption issue. Versions 1.31.9 and 1.30.7 contain the
fix. See the [NGINX security advisories](https://nginx.org/en/security_advisories.html).

## Executive summary

The strongest indicator is not a particular URI or User-Agent. It is a
combination of:

- abnormal volumes of HTTP/2 client traffic over relatively few long-lived
  TLS connections;
- bursts of large `HEAD` requests and HTTP `206 Partial Content` responses;
- repeated stream resets and unusual flow-control behavior;
- multiple auxiliary connections reaching the same NGINX instance; and
- an NGINX worker spawning `/bin/sh -c ...` or another unexpected executable.

The exact URI, request counts, traffic volume, connection count, and marker
filename are PoC-specific and should not be treated as universal signatures.

## Supplied PoC behavior

The RCE client performs the following operations:

- negotiates TLS 1.3 with ALPN `h2`;
- uses `/index.html` as its profiled static resource;
- sends approximately 119.02 GiB of HTTP/2 plaintext during a successful run;
- sends 8,589,934,593 legal connection `WINDOW_UPDATE` frames;
- opens one principal connection and 16 auxiliary TLS connections;
- leaks process memory and resolves NGINX and libc addresses in-band; and
- replaces a request-pool cleanup callback with `system(command)`.

The important profile-specific values are recorded in
[`golden-nginx-1.31.8-debian13-amd64.json`](https://github.com/sfewer-r7/CVE-2026-123007/blob/main/exploit/profiles/golden-nginx-1.31.8-debian13-amd64.json).
They include 74 initial requests, 960 maximum-sized carrier frames, 96 rotating
flow-control owners, 262,144 TLS KeyUpdates, and 16 auxiliary connections.

The command runs with the NGINX worker's credentials. In the demonstrated
container this is UID/GID 101. The PoC does not inherently elevate execution
to the root account used by a typical NGINX master process.

## NGINX access-log artifacts

### Default combined logs

The default `combined` access log hides many of the strongest indicators. An
attempt can produce lines that appear ordinary:

```text
203.0.113.10 - - [19/Nov/2026:02:03:01 +0000] "GET /index.html HTTP/2.0" 200 896 "-" "-"
203.0.113.10 - - [19/Nov/2026:02:03:02 +0000] "GET /index.html HTTP/2.0" 206 127 "-" "-"
203.0.113.10 - - [19/Nov/2026:02:03:03 +0000] "HEAD /index.html HTTP/2.0" 200 0 "-" "-"
203.0.113.10 - - [19/Nov/2026:02:03:04 +0000] "GET /index.html HTTP/2.0" 206 0 "-" "-"
```

Expected characteristics of the supplied PoC include:

- HTTP/2 requests without a User-Agent or Referer;
- an initial group of ordinary `GET` responses;
- `206` responses for small ranges, including one-byte responses;
- hundreds of `HEAD` requests whose response body size is zero;
- repeated `206` responses with zero bytes delivered because their streams
  are reset or remain flow-controlled;
- a later fan-out to 16 additional TLS connections; and
- requests that may only be written to the access log when a stream or
  connection is closed.

The RCE PoC generates approximately 322 unusually large `HEAD` requests on
the principal connection. The largest are formed from three maximum-sized
HTTP/2 header frames and represent roughly 48 MiB of compressed header-block
traffic per request. These requests decode to an ordinary-looking method and
path, so their size is invisible in the default combined format.

Reset or incomplete requests may be recorded differently depending on how far
request construction progressed. Possible outcomes include:

- a normal `200` or `206` status with zero response-body bytes;
- delayed logging when the connection is closed;
- an incomplete-request status; or
- no access-log record for a header block that never became a request.

### Recommended extended logging

NGINX supports variables such as `$request_length`, `$request_time`,
`$connection`, `$connection_requests`, `$request_completion`, and
`$server_protocol`. See the
[NGINX log-module documentation](https://nginx.org/en/docs/http/ngx_http_log_module.html).

An incident-oriented format can expose the higher-confidence indicators:

```nginx
log_format incident
  '$time_iso8601 src=$remote_addr conn=$connection creq=$connection_requests '
  'proto=$server_protocol req="$request" status=$status '
  'body=$body_bytes_sent length=$request_length time=$request_time '
  'complete="$request_completion" range="$http_range" ua="$http_user_agent"';
```

Useful detection logic includes:

- quick aggregate bursts of `HEAD` requests over HTTP/2;
- individual `HEAD` request lengths in the multi-megabyte range;
- bursts of `206` responses, especially with zero or one response-body byte;
- many incomplete requests or stream cancellations;
- large volumes of inbound traffic on a small number of TLS connections;
- multiple related connections arriving near the end of the attempt; and
- HEAD and partial-content bursts occurring within the same short time range.

Detection should aggregate across clients and paths. An adversary may
distribute connections among several source addresses or select a different
static resource instead of `/index.html`.

The companion `nginx-ioc-scan` utility developed alongside this report
implements these aggregate access-log detections.

## NGINX error-log artifacts

A clean successful exploit may produce no unmistakable error-level NGINX
message. The PoC intentionally constructs mostly protocol-valid HTTP/2 frames,
and normal client stream resets are not necessarily logged at standard levels.

A crash or failed exploit is more visible. The standalone trigger produced:

```text
2026/11/06 16:46:45 [alert] 1#1: worker process 9 exited on signal 11 (core dumped)
```

This result is documented in
[`NGINX_HTTP2_STANDALONE_REPRODUCTION.md`](https://github.com/sfewer-r7/CVE-2026-123007/blob/main/NGINX_HTTP2_STANDALONE_REPRODUCTION.md).
The full RCE path may also crash the corrupted worker after executing the
command, but a worker crash is not required for successful exploitation.

With an NGINX debug build and debug logging, HTTP/2 frame processing can be
visible, including repeated type-8 `WINDOW_UPDATE` frames. Enabling debug
logging broadly during an attack of this volume can generate excessive logs
and materially affect service behavior, so it should not be treated as the
primary production detection mechanism.

## systemd journal and coredump artifacts

On a systemd host, likely observations include:

- an NGINX worker-exit alert in `journalctl -u nginx` if NGINX writes its error
  log to stderr or the journal;
- no NGINX detail in the journal when the distribution writes errors only to
  `/var/log/nginx/error.log`;
- an NGINX master that remains active while it starts a replacement worker;
- no service restart or failed-unit state, because a worker crash does not
  necessarily terminate the master; and
- systemd-coredump metadata for an NGINX process terminated by `SIGSEGV`.

When systemd-coredump is enabled, useful fields include:

```text
COREDUMP_EXE=/usr/sbin/nginx
COREDUMP_SIGNAL_NAME=SIGSEGV
COREDUMP_SIGNAL=11
COREDUMP_UID=<nginx-worker-uid>
COREDUMP_CMDLINE=nginx: worker process
```

The entry may also include the service cgroup, executable mappings, open file
descriptors, and a stack trace. The structured coredump message ID is
`fc2e22bc6ee647b6b90729ab34a250b1`. See the
[systemd-coredump documentation](https://freedesktop.org/software/systemd/man/latest/systemd-coredump.socket.html).

A successful command does not automatically generate a journal entry. Output
from the command may appear in the NGINX error log, container log, or journal
because the spawned process inherits the worker's file descriptors. Silent
commands such as `touch` produce no such output.

systemd also does not ordinarily record every `execve`. Audit, eBPF, or EDR
process telemetry is needed to reliably recover short-lived child processes
and their command lines.

## Successful exploitation in the process list

The PoC constructs an NGINX cleanup record whose callback is libc `system` and
whose argument is the attacker-supplied command. During execution, the process
tree will typically resemble:

```text
nginx: master process /usr/sbin/nginx
└─ nginx: worker process
   └─ /bin/sh -c -- <attacker-command>
      └─ <command or payload>
```

Important process characteristics include:

- the shell or payload is a child of an NGINX worker, not the master;
- it runs as the worker account, commonly `nginx` or `www-data`;
- it initially remains in the NGINX service cgroup and namespaces;
- it inherits the worker's environment, resource limits, working directory,
  and open descriptors;
- the worker waits for `system()` to return and may stop handling events while
  a long-running command executes; and
- a shell may optimize a simple command by replacing itself, causing telemetry
  to show the worker directly parenting the final executable.

The example `touch` command can complete in milliseconds and will probably be
missed by periodic `ps` collection. Process-execution telemetry is therefore
more reliable than live process sampling. A high-confidence analytic is an
NGINX worker spawning a shell, interpreter, downloader, network utility, or
other executable unrelated to normal web serving.

The marker `/tmp/rapid7-nginx-h2-proof-01` is only an example from the
reproduction instructions. The exploit accepts an arbitrary command and does
not otherwise create a fixed file or payload on the victim.

## Triage commands

```sh
journalctl -u nginx --since '2 hours ago'
journalctl MESSAGE_ID=fc2e22bc6ee647b6b90729ab34a250b1 --since '2 hours ago'
coredumpctl list nginx
zgrep -hE '"(GET|HEAD) .* HTTP/2\.0" (200|206)' /var/log/nginx/access.log*
ps -eo user,pid,ppid,lstart,etime,args --forest
systemd-cgls /system.slice/nginx.service
```

For retrospective investigation, correlate the following around the same time:

1. aggregate HTTP/2 HEAD and 206 bursts;
2. unusually high inbound TLS traffic;
3. additional connections reaching the same NGINX instance;
4. an NGINX worker crash or replacement; and
5. an unexpected shell or executable launched by an NGINX worker.

## Indicator reliability

| Indicator | Reliability | Notes |
|---|---:|---|
| NGINX worker launching `/bin/sh -c` | High | Strong successful-execution evidence. |
| NGINX worker launching an unexpected executable | High | Shell optimization may remove the visible intermediate shell. |
| SIGSEGV and worker replacement | Medium-high | Strong attempt or corruption evidence, but success does not require a crash. |
| Large aggregate HTTP/2 HEAD bursts plus 206 bursts | Medium-high | Generalized network behavior; correlate with request length and volume. |
| Tens of GiB received on long-lived HTTP/2 sessions | Medium-high | Strong for this strategy, but a more efficient exploit could differ. |
| Sixteen auxiliary connections | Medium | Specific to the supplied heap-reclaim strategy. |
| `/index.html` requests | Low | Profile-specific and easily changed. |
| `/tmp/rapid7-nginx-h2-proof-01` | Low | Demonstration command only. |

The worker-child execution lineage and aggregate flow-control traffic are the
most durable indicators. Exact URLs, source addresses, filenames, counts, and
byte volumes should be treated as supporting context rather than required
conditions.
